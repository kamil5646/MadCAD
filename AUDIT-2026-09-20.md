# MadCAD 6.5.22 — audyt repozytorium i plan dalszych prac

Data audytu: 2026-09-20  
Repozytorium: `kamil5646/MadCAD`  
Sprawdzony commit: `1127f4e3dae5776d43800613a1869f9821305ba3` (`main`, `v6.5.22`)

## Wniosek wykonawczy

MadCAD ma już bardzo szeroki zakres funkcjonalny, prawdziwy kernel OpenCascade,
historię parametryczną, format projektu z migracjami, rozbudowane testy core i
duży zestaw scenariuszy Electron. Projekt nie potrzebuje teraz kolejnej fali
przycisków. Największą wartość da ustabilizowanie toru `main -> CI -> release ->
strona`, ujednolicenie modelu konta/licencji i zmniejszenie ryzyka zmian w kilku
monolitycznych plikach.

Aktualnie produkt jest bliżej szerokiego prototypu profesjonalnego CAD niż
gotowego zamiennika Autodesk Fusion. W wielu domenach istnieje pionowy scenariusz
i test, ale nie ma jeszcze wystarczających dowodów niezawodności na dużych,
zewnętrznych projektach oraz długiej pracy użytkownika.

  224 testy core, build UI, `verify:repository` i

## P0 — zrobić przed kolejnym wydaniem

### 1. Przywrócić zielony `main`

Przenieść poprawkę `invokeVerificationHook()` do
`scripts/verify-reference-repair-wizard.cjs`, uruchomić lokalny scenariusz kilka
razy, a następnie potwierdzić zielony shard projektu na Windows w GitHub Actions.
Nie wystarczy zielony workflow wydawniczy: zwykły CI `main` pozostaje źródłem
prawdy dla rozwoju.

Kryterium odbioru:

- cały `MadCAD CI` na `main` jest zielony;
- artefakt diagnostyczny scenariusza ma dokładny etap błędu;
- ponowne uruchomienie nie jest potrzebne do uzyskania sukcesu.

### 2. Ujednolicić ochronę gałęzi z nazwami aktualnych jobów

Branch protection wymaga starych nazw `Desktop modeling E2E (...)`, podczas gdy
workflow raportuje `Desktop E2E modeling (...)`. Wymaga też tylko dwóch z pięciu
wariantów instalatora. Aktualne PR-y są oznaczone jako `BLOCKED`.

Należy zaktualizować wymagane kontrole do faktycznie emitowanych nazw i jawnie
ustalić, które z pięciu paczek są blokadą merge. Warto również włączyć jedną
recenzję dla zmian w Electronie, workflowach, licencji i wydaniach oraz
`enforce_admins`.

### 3. Naprawić publikację strony produkcyjnej

Repo zawiera stronę 6.5.22, lecz domena produkcyjna serwuje 6.5.5. Trzeba ustalić
jedno źródło wersji i automatyczny deployment po udanym wydaniu. Po wdrożeniu
sprawdzić w przeglądarce tekst wersji i każdy bezpośredni link do paczki.

Kryterium odbioru:

- domena pokazuje wersję równą `package.json` i latest release;
- linki Windows/macOS/Linux prowadzą do istniejących artefaktów tej wersji;
- release workflow lub osobny kontrolowany workflow wykonuje deployment;
- kontrola kończy się testem HTTP i testem widoku strony.

### 4. Wybrać jeden rzeczywisty model konta i licencji

Obecny program blokuje wejście bez konta (`accessAllowed`), klient licencji
łączy się z usługą i przechowuje chroniony token. Strona produkcyjna oraz
`madcad-2d/README.md` również mówią o wymaganym koncie. Jednocześnie główny
`README.md`, część tekstów i opis repo deklarują brak konta i aktywacji.

To nie jest kosmetyka: użytkownik przed instalacją otrzymuje sprzeczne warunki.
Należy podjąć decyzję produktową, a potem z jednego źródła wygenerować README,
stronę, dialog aplikacji, LICENSE/EULA/PRIVACY i test spójności.

### 5. Nie aktualizować kernela przez zwykły Dependabot merge

PR #53 podnosi `replicad-opencascadejs` z 0.23 do 1.1 i psuje core/build na
wszystkich trzech systemach. To migracja kernela, nie aktualizacja zależności.
Wymaga osobnej gałęzi, inwentaryzacji API, golden B-Rep, plików zewnętrznych,
porównania objętości/topologii oraz pełnego E2E.

PR-y #54 i #68 przechodzą większość kontroli, ale padają na Windowsowym shardzie
modelowania. Po ustabilizowaniu bazowego CI należy wykonać rebase i ponowną
ocenę każdego PR osobno. Zewnętrzny check Cloudflare `madcadtoken` został
odłączony 2026-09-21 przez odinstalowanie aplikacji GitHub Cloudflare.

## P1 — stabilność produktu

### 6. Zamrozić rozrost funkcji i testować scenariusze użytkownika

MadCAD deklaruje już szkic, bryły, powierzchnie, mesh, blachy, plastic, Form,
złożenia, dokumentację, CAM, symulację i druk 3D. Następny etap powinien mierzyć:

- otwieranie i przebudowę dużych projektów;
- długie sesje z setkami operacji i wieloma undo/redo;
- odporność na utratę referencji i naprawę historii;
- pamięć, czas uruchomienia i czas przebudowy;
- import rzeczywistych STEP/DWG/DXF/STL/3MF z różnych programów;
- zapis, crash recovery i upgrade dokumentów między wydaniami;
- ręczne testy instalatora, aktualizatora i odinstalowania na fizycznych
  Windows/macOS/Linux.

Każda domena powinna mieć jawny poziom: `eksperymentalna`, `beta`, `stabilna`.
Samo istnienie przycisku i pojedynczego fixture nie oznacza zgodności z Fusion.

### 7. Podzielić monolity wzdłuż granic domen

Największe pliki to:

- `ModelingWorkspace.jsx` — 8229 linii;
- `ModelViewport.jsx` — 3443 linie;
- `cad-worker.js` — 3117 linii;
- `document.js` — 2111 linii;
- `i18n.js` — 2028 linii.

Build tworzy chunk `ModelingWorkspace` 1,32 MB po minifikacji (355 kB gzip) i
worker 650 kB. Zalecana kolejność wydzieleń: kontroler dokumentu i dirty-state,
rejestr/maszyna stanów poleceń, persistence, import/export, dialogi i panele,
następnie scena/picking/manipulatory, a na końcu adaptery kernela. Każde
wydzielenie ma zachować istniejący desktop E2E.

### 8. Zaostrzyć testy tam, gdzie agregat coverage myli

Utrzymać globalny próg, ale dodać progi per moduł dla persistence, dokumentu,
topologii, importu i mesh. Testy hooków wewnętrznych powinny uzupełniać, nie
zastępować, scenariusze oparte o zachowanie użytkownika. Dla ciężkich testów
Electron należy raportować dokładny krok, czas i zrzut zamiast ogólnego
`Script failed to execute`.

### 9. Podpisy i bezpieczna aktualizacja

Zdobyć certyfikat Authenticode oraz Apple Developer ID/notaryzację, ograniczyć
entitlements do niezbędnego minimum i sprawdzić aktualizację z poprzedniej
podpisanej wersji do następnej. Do tego czasu README i strona muszą jasno mówić,
że paczki są niepodpisane.

## P2 — utrzymanie i kierunek produktu

### 10. Zdefiniować aktywną roadmapę

`ROADMAP.md` i `BACKLOG.md` dokumentują głównie historię ukończonych funkcji.
Nowa roadmapa powinna mieć jeden aktywny pionowy cel i mierzalne kryteria.
Proponowana kolejność:

1. `R6.5-stability` — zielony CI, spójna licencja, aktualna strona;
2. `R6.6-reliability` — duże projekty, recovery, import zewnętrzny, performance;
3. `R6.7-maintainability` — podział workspace/viewport/worker;
4. dopiero później nowe funkcje konkurujące z Fusion.

### 11. Uporządkować repozytorium

- zamknąć lub scalić pięć otwartych PR-ów;
- usunąć zdalne gałęzie po scaleniu i zarchiwizować porzucone eksperymenty;
- skonfigurować automatyczne usuwanie gałęzi po merge;
- utrzymać brak starego Cloudflare checku przy kolejnych PR-ach;
- aktualizować duże zależności pojedynczo, z planem migracji;
- poprawić stopkę `docs/index.html`, która nadal pokazuje `MadCAD 6.3`.

## Co zachować

- lokalny format projektu i brak telemetrii projektów;
- transakcyjną historię i ostatni poprawny wynik po błędzie;
- trwałe referencje B-Rep i kreator naprawy;
- prawdziwe testy OpenCascade i round-trip formatów;
- pinowanie GitHub Actions do pełnych SHA;
- osobne shardy Electron i artefakty diagnostyczne;
- jawne ograniczenia funkcji zamiast atrap.

## Minimalna bramka każdej zmiany

Z katalogu `madcad-2d`:

```bash
npm ci
npm run lint
npm test -- --run
npm run test:core:coverage
npm run build:ui
npm run verify:repository
npm run verify:product-completeness
git diff --check
```

Zmiana geometrii, Electron, licencji, importu albo wydania wymaga dodatkowo
właściwego scenariusza desktopowego. Wydanie jest zakończone dopiero po zielonym
workflow, obecności wszystkich artefaktów i sprawdzeniu produkcyjnej strony.
